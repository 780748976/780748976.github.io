>
> 一句话版本：**GraphRAG 用"离线预生成社区报告 + 在线 map-reduce"回答全局问题，token 贵、建图慢、更新重；LightRAG 把社区摘要这一层彻底砍掉，改成"在线双路检索 + 统一重排"，换来增量更新和近乎一个数量级的 token 节省——代价是牺牲了 GraphRAG 最强的"全局综合能力"。**

## 一、先看设计哲学的分岔点

两个系统要解决的问题是一样的：**给 LLM 喂的检索上下文，怎么从"一堆散落的 chunk"升级成"有结构的、跨文档的知识"？**

但两家走了完全相反的两条路：

```
GraphRAG（微软，2024）
  "先建好城市模型，再回答任何问题"
  索引期：实体图 → Leiden 层次社区 → 每个社区预生成报告（离线，一次性的重）
  查询期：局部问题走实体局部检索；全局问题走全量社区报告 map-reduce（在线，每次的重）

LightRAG（HKU，2024）
  "不建城市模型，每次问路时现查地图"
  索引期：实体图 + 关系图（离线，相对轻）
  查询期：双路（低层/高层关键词）并发检索 + 多源 chunk 合并 + rerank（在线，每次都轻）
```

一句话概括哲学差异：

> **GraphRAG 把"理解语料"的活提前干完（离线重），查询时直接消费预计算结果；LightRAG 把"理解语料"的活推迟到查询时现算（在线轻），用更聪明的检索来补偿。**

这个分岔衍生出三组底层差异，本文依次拆：**① 图怎么建**（索引期）、**② 查询怎么走**（检索期）、**③ 更新怎么维护**（生命周期）。

## 二、索引期对比：一张图 vs 三份料

### 2.1 GraphRAG：从图到社区，再到"社区报告"

GraphRAG 的索引流水线（官方数据流图）比 LightRAG 多了整整两个重阶段：

```
① chunking → TextUnits          （文档切块，类似 LightRAG 的 chunk）
② 实体/关系/声明抽取            （每块调 LLM 抽实体、关系、covariates 声明）
③ 图构建                        （实体=节点、关系=边，合并同名实体）
④ 层次社区检测（Leiden 递归）   ★ LightRAG 没有
⑤ 社区报告生成（每社区调 LLM）  ★ LightRAG 没有
⑥ 实体描述向量化                （供局部搜索语义召回）
```

**第④步：Leiden 层次社区检测。** 在实体关系图上递归跑 Leiden 算法做社区聚类，直到每个社区的规模低于阈值。结果是一棵**层次社区树**：

```
整个语料
├── 社区 C1（level 0，最粗）          ← 覆盖最大主题
│   ├── 子社区 C1-1（level 1）
│   │   ├── 实体 A、实体 B            ← 叶子是原始实体
│   │   └── 实体 C
│   └── 子社区 C1-2
└── 社区 C2
```

层级越深越具体、越浅越宏观。这棵树是 GraphRAG 回答"全局问题"的底气——**它在索引期就把"语料里有哪些主题群"这件事给算出来了**。

**第⑤步：社区报告（community report）。** 对**每个社区**（不止叶子）调一次 LLM，把该社区内所有实体的描述、关系、声明压缩成一篇摘要，包含社区主题、关键实体、关键关系、重要声明等字段。这份报告在索引期就固定下来，查询期直接复用。

> **这一步是 GraphRAG token 贵的第一来源**：社区的个数 = 调 LLM 的次数，而且报告本身要读社区内全部实体/关系，每次摘要的输入 token 也很大。官方对小说语料建索引的 token 成本常是语料本身的几十倍量级（取决于重叠与重试）。

### 2.2 LightRAG：只有一张图，没有社区

LightRAG 的索引流水线（上篇《增删改》已拆过）只有：

```
① chunking                    （token 滑窗，512 token）
② 实体/关系抽取               （每 chunk 调 LLM，带 cache）
③ 图合并                      （同名实体去重 + LLM 重摘要 + source_id 拼接）
④ 三份向量化                  （chunk 向量 / 实体向量 / 关系向量）
```

**没有社区检测、没有报告生成**。LightRAG 认为：社区报告是"提前把图给总结掉了"，这一总结不仅贵，还**不可增量**——新增一篇文档，社区结构会变，报告要重新生成一大片。

### 2.3 索引期成本对比

| 维度 | GraphRAG | LightRAG |
|---|---|---|
| LLM 调用次数 | 抽取 + **每社区一次摘要**（社区可到数百上千） | 抽取 + 合并时少数 summarize |
| 抽取粒度 | 每 TextUnit 抽实体/关系/**声明** | 每 chunk 抽实体/关系 |
| 向量库 | 实体描述一个 | chunk / 实体 / 关系三个 |
| 图结构 | 实体图 + **社区树 + 报告表** | 实体图（含关系边） |
| 增量友好度 | 差（社区要重算重摘要） | 好（见第五节） |

## 三、查询期对比：map-reduce 全量扫描 vs 双路在线检索

这是两家的核心分水岭，也是"底层原理"最值得掰开的地方。

### 3.1 GraphRAG 的两种搜索

GraphRAG 查询分两档，各回答一类问题：

**Local Search（局部搜索）——回答"具体问题"：**

```
query embedding
  → 实体向量库召回 top-k 相关实体（fuzzy matching 实体名）
  → 以这些实体为锚点，图里取一跳邻居实体 + 邻居关系
  → 同时取这些实体所属社区的报告（一份）
  → 取这些实体关联的 TextUnit（原文 chunk）
  → 按 token 预算混合排序 → LLM
```

Local Search 的上下文由四部分按比例拼成：**TextUnit + 关系 + 实体 + 社区报告**（默认 `text_unit_prop=0.5, community_prop=0.1`，即一半原文 chunk、一成社区报告）。这和 LightRAG local 模式几乎同构——锚定实体、展开邻居、反查原文。**注意：LightRAG 的 local/global 模式基本是 GraphRAG Local Search 的简化版**。

**Global Search（全局搜索）——回答"宏观综合问题"：**

```
整个语料的所有社区报告（取某一层级，默认 level 0 最粗）
  → MAP 阶段：报告切成小段，逐段送 LLM，各生成"部分回答 + 重要性评分"
  → 按评分过滤/排序部分回答
  → REDUCE 阶段：把保留的部分回答拼起来，再一次 LLM 生成最终答案
```

关键点：**Global Search 的输入不是"检索出来的"东西，而是"索引期就生成好的全部社区报告"**。它不做向量检索——它在 map-reduce 所有报告。所以：

> - 回答"这堆文档里主要讲了哪几个主题""整体趋势是什么"这类**要纵观全库**的问题，GraphRAG 是碾压级的，LightRAG 基本答不好。
> - 但每次 Global Search 都要把**全量报告**过一遍 LLM，token 成本随语料规模线性涨——这是 GraphRAG token 贵的第二来源（在线侧）。

### 3.2 LightRAG：把"全局"降级为"高层关键词检索"

LightRAG 没有社区，怎么回答"全局问题"？答案是**不真全局，用关键词分层假装全局**：

```
用户问题："这个领域这两年有什么趋势？"
  → LLM 抽出高层关键词（hl）：["技术趋势", "领域发展"]
  → hl 去关系向量库 relationships_vdb 召回"主题级"关系
  → 关系反查实体 + 反查 chunk
  → 进统一的 process_chunks 流水线（rerank / 过滤 / 截断）
```

（细节见《LightRAG 四条检索链路》第 2.2 节。）

LightRAG 的"global"和 GraphRAG 的"global"**根本不是一回事**：

| | GraphRAG Global | LightRAG global |
|---|---|---|
| 检索信号 | 全部社区报告（预先总结） | 高层关键词（LLM 现抽） |
| 覆盖范围 | 全语料（报告覆盖所有社区） | top-k 关系（≈40 条） |
| 成本 | 随语料规模线性涨 | 固定 token 预算 |
| 能答"全库主题"吗 | 能，设计目标 | 弱，只覆盖被抽成关系的那部分 |

**LightRAG 用"关键词分层"这一个廉价机制，替代了 GraphRAG 用"社区报告全量扫描"实现的全局能力**——代价是真正的全局综合（跨全库归纳）做不了，收益是查询成本几乎与语料规模无关。

### 3.3 检索管道的结构对比

把两家查询期的管道并排画：

```
GraphRAG Local:
  query → 实体向量召回 → 邻居展开 → {TextUnit, 关系, 实体, 社区报告} 混拼 → LLM

GraphRAG Global:
  query → 全部社区报告 → MAP(报告分段→部分回答+评分) → 过滤 → REDUCE(拼起来→最终答案)

LightRAG local / global / hybrid / mix:
  query → LLM抽 ll/hl 关键词 → 实体/关系向量库双路召回
       → token 截断 → chunk 反查合并 → rerank → 动态预算裁剪 → LLM
```

同构点很明显：**LightRAG 的 local = GraphRAG Local Search 去掉社区报告**（community_prop 置零）；**LightRAG 的 global = GraphRAG Global Search 去掉全量扫描，换成 top-k**。而 LightRAG 的 hybrid/mix（双路 + rerank）是 GraphRAG 没有的增量设计——它用"多路召回 + 独立 rerank 模型统一排序"来补偿缺失的社区报告。

### 3.4 token 成本的账：一次查询谁更贵

假设 1000 个文档、抽出了 8000 个实体、社区检测后 level 0 有 200 个社区报告：

```
GraphRAG Global Search（回答"全库主题"）:
  输入 = 200 份报告 ≈ 假设 150 token/报告 = 30,000 token
  MAP 阶段还要分段各调一次 LLM + REDUCE 一次
  → 单次查询总成本：数万 token + 数十次 LLM 调用

LightRAG hybrid（回答同样的问题）:
  输入 = 截断后的实体(6000t) + 关系(8000t) + chunk(动态预算, 上限约 21k)
  → 单次查询总成本：固定 ≤ 30,000 token，1 次 LLM 调用
```

注意两边口径不同：GraphRAG 是"**为回答全局问题，把全量预总结都读一遍**"，LightRAG 是"**用固定预算精选 top-k**"。GraphRAG 的答案更全面（官方论文的核心卖点就是 comprehensiveness/diversity），LightRAG 更便宜更可控。

## 四、检索质量的底层逻辑：预总结 vs 在线重排

两家对"为什么检索结果靠谱"给出了不同的答案，这是最深的原理分歧：

### 4.1 GraphRAG 的答案：**离线预总结 = 把"全局相关性"提前固化**

GraphRAG 认为，跨文档的宏观知识（"A 与 B 公司的关系" "整个行业的格局"）**分散在大量 chunk 里，靠在线检索拼不齐**。所以它在索引期就把这些宏观知识浓缩进社区报告——**相关性在离线就判定完了，查询期只是搬运**。

- 优点：全局问题答得全、答得有结构
- 缺点：① 报告生成贵；② **报告里的知识是"当时的语料"快照**，语料一更新，报告可能过时；③ 报告是 LLM 二次压缩，有信息损失（细节丢失在摘要里）

### 4.2 LightRAG 的答案：**在线双路检索 + rerank = 把"局部相关性"现算现用**

LightRAG 认为，与其提前总结（贵、不可增量、有过时风险），不如**查询时多路召回（实体路 + 关系路 + 纯向量路）、用独立 rerank 模型在统一相关性维度上现排**：

- 优点：① 索引便宜；② 增量友好；③ rerank 的"相关性判断"基于**当前 query**，比离线报告"针对语料"的判断更贴合具体问题
- 缺点：**没有"全库视角"**——rerank 再准，也只在 top-k 候选里准；候选池外的东西（比如没被抽成实体、又不在 top-k chunk 里的宏观结论）永远进不来

### 4.3 一句话总结质量差异

> **GraphRAG 的强项是"广度"（全库综合），LightRAG 的强项是"准度"（局部精检）。** GraphRAG 牺牲了增量性和成本换广度，LightRAG 牺牲了广度换增量性和成本。两者不是谁替代谁，是同一个目标的两个极端解。

## 五、更新链路对比：全量重建 vs 删旧插新

这是选型时最实际的一刀。

### 5.1 GraphRAG：增量更新=部分重建，社区报告是老大难

GraphRAG 官方提供 incremental index：只对**新增文档（按 title 去重）**重跑抽取，然后跑 8 个 update-merge workflow 把增量合并进原索引，其中包括 `update_communities` 和 `update_community_reports`。

但有两个硬伤（官方文档也承认）：

```
① 增量检测只看 title，不看内容
   同 title 但内容改了 → get_delta_docs 检测不到 → 不重索引（官方明说的核心局限）

② 新增文档会改变图结构 → 社区划分会变 → 受影响社区的【报告要重新生成】
   报告重生成 = 又一轮离线重活，且"哪些社区受影响"很难精确界定
   → 工程上经常被迫"全量重建"
```

所以 GraphRAG 的实际更新体验：**小改 = 大重建**。

### 5.2 LightRAG：删旧插新 + LLM cache 伪装增量

LightRAG 的更新（上篇《增删改》已拆透）核心是：

```
改文档 = 删旧（source_id 集合减法 → 三态决策：不动/重建/整删）
       + 插新（全量重切 chunk + 重抽实体，但……）
          └─ LLM cache key = chunk_id，内容没变的 chunk 直接命中 cache 跳过 LLM
          └─ 实际 LLM 成本 ≈ 只抽真正改动的那几个 chunk
```

**关键差异**：LightRAG 没有"社区"这一层，更新时只需要维护实体/关系/source_id，**不存在"报告重生成"这种波及面不可控的步骤**——更新成本与改动量成正比，而不是与语料规模成正比。

### 5.3 更新对比总表

| 维度 | GraphRAG | LightRAG |
|---|---|---|
| 增量检测 | title 比对（内容变更检测不到） | file_source 去重 + content_hash |
| 改动内容怎么办 | 重跑该文档抽取 + 社区报告重生成 | 删旧插新，cache 命中跳过 |
| 更新波及面 | 社区级（不可控） | 实体级（source_id 减法精确到点） |
| 小改动成本 | ≈ 大重建 | ≈ 只重抽改动的 chunk |

## 七、怎么选：一张决策表

不是"谁更好"，是"你的约束在哪边"：

| 你的情况 | 推荐 | 理由 |
|---|---|---|
| 要答"整个语料讲什么、有哪些主题、趋势如何" | **GraphRAG** | 这正是社区报告 + 全局搜索的设计目标 |
| 语料经常增删改，想要增量更新 | **LightRAG** | 无社区层，更新成本与改动量成正比 |
| token 成本敏感（自掏腰包 / 大语料） | **LightRAG** | 查询固定预算，索引期也便宜得多 |
| 语料不大且基本不变，但问题宏观 | **GraphRAG** | 贵一次（索引）换每次查询的全面 |
| 知识库问答、要引用、要 rerank 精排 | **LightRAG** | 四模式 + 统一 rerank 流水线更顺手 |

> 实践中还有一个混合派：**用 GraphRAG 的社区报告喂全局问题，用 LightRAG 式的实体路喂局部问题**——很多生产系统（包括官方后来出的 DRIFT Search，本质是"局部搜索 + 社区信息补广度"）都是在朝这个方向收敛。理解了本文的底层原理，你就能看懂这些"缝合方案"各自缝的是哪一块。

## 八、灵魂总结

回到开头那句话，用一张图收束全文：

```
GraphRAG:  索引期"重理解"（图→社区→报告）  查询期"消费"（全量 map-reduce）
           哲学：把全局相关性提前固化，贵在前期

LightRAG:  索引期"轻理解"（图而已）         查询期"现算"（双路检索+rerank）
           哲学：把相关性判断推迟到每次查询，贵在灵活
```

三个记忆锚点：

1. **社区报告是 GraphRAG 的一切**——它既是全局能力的来源，也是 token 贵、更新难的根源；LightRAG 砍掉它，等于同时砍掉了"全局能力"和"历史包袱"。
2. **GraphRAG 的 global 是"全量预总结扫描"，LightRAG 的 global 是"关键词 top-k 检索"**——同名不同物，别再被名字骗了。
3. **选择 = 在"广度 / 增量 / 成本"三个约束里取两个**：GraphRAG 取广度和准度丢增量，LightRAG 取增量和成本丢广度。
