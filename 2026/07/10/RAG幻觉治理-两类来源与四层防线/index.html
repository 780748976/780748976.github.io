RAG 幻觉治理：两类来源 × 四层防线，从「先治检索」到「生成后核查」

上一篇我们聊了检索侧的 Query Rewrite。这篇聊 RAG 落地时最让人头疼的问题：幻觉。

很多人有个根深蒂固的误解：「做了 RAG 就不会有幻觉了」。实际完全不是这样——RAG 只是把知识库的内容塞进了 prompt，但塞进去不等于 LLM 会老老实实照着说。LLM 有自己的预训练知识储备，当 prompt 里的资料和它”学过”的不一致、甚至根本就没召回到相关内容时，它就会绕开资料自己发挥。

一句话版本：RAG 里的幻觉有两个完全不同的来源——检索层没找到（LLM 靠猜）和生成层超发挥（LLM 自由发挥）；对应的四层防线从「最便宜」到「最严格」依次是：Prompt 强约束 → 检索质量门控 → 生成后引用核查 → 结构化溯源，而治幻觉的根本是先治检索。

一、先搞清楚：幻觉到底从哪来

「幻觉」就是模型一本正经地说了一件压根不存在的事。它不是撒谎，它只是在「预测下一个词」——当没有可靠依据时，就会拼凑出一个”听起来合理”的答案。

关键问题：RAG 不是已经把知识库内容塞进 prompt 了吗，LLM 为什么还会编？ 因为 RAG 里有两道各自独立的环节，幻觉可能从任何一环漏进来：

来源一：检索层没找到，LLM 靠「猜」回答。

RAG 的前提是「检索到相关内容再生成」。但如果检索失败，prompt 里是空的或全是无关内容，LLM 不会说「我不知道」——它会用预训练时见过的知识编一个看起来像答案的东西，而且说得很自信，用户根本看不出来。

例子：知识库里记录的退款政策是「7 天无理由退款」，但某次检索没召回到这个 chunk，LLM 用自己的「知识」给出了「30 天退款」的答案。用户按这个信息操作，退款失败——这就是检索层幻觉造成的实际损失。

来源二：检索到了，但 LLM 没有严格照着说。

这种幻觉更隐蔽、也更常见。相关的 chunk 确实被召回了，但 LLM 生成时”超发挥”了：把资料内容当基础，加上自己的推断、补充原文没有的细节、甚至把两段不相关的信息拼出一个”更完整”的答案。读者很难分辨哪句来自文档、哪句是 LLM 加的。

这两种幻觉根源不同，解法也不一样。下面四层防线，从「成本最低」到「机制最严格」依次递进。

二、防线一：Prompt 强约束——事前立规矩（最便宜）

这是成本最低、最容易上手、效果也立竿见影的方案。 很多人搭 RAG 时只是把 chunk 塞进 prompt，然后问「请回答这个问题」，并没有明确约束 LLM 的行为——LLM 就会觉得”这些资料只是参考，我可以结合自己的知识一起回答”，幻觉就这样产生了。

修复方法很简单：在 system prompt 里明确立规矩：

每条规则都有它的道理：

  • **①是让 LLM “知道自己的边界”**：明确告诉它，你只是个传话人，不是百科全书
  • ②是给 LLM 一个「合法的逃生出口」：资料里没有答案时说”不知道”，比编一个看起来合理的答案好得多——这条规则允许 LLM 优雅地认怂
  • ③是让 LLM 主动对照原文：相当于给它加了一个自检动作，哪句话来自哪条资料必须说清楚

这个方案压制的是「生成层幻觉」，对「检索层幻觉」帮助有限——如果 prompt 里根本没有相关内容，再强的约束也顶不住 LLM 瞎编。所以还需要下一道防线。

三、防线二：检索质量门控——检索质量差就拒答（前事拦截）

防线一解决了「LLM 超发挥」，但如果检索这一步就失败了，prompt 里全是无关内容，光靠 Prompt 约束是拦不住的。那怎么办？

与其让 LLM 在低质量上下文里强行生成一个”可能是错的答案”，不如直接告诉用户「知识库里没有这个信息」。前者让用户误以为答案是对的，后者虽然看起来不那么智能，但至少不会给用户错误信息——答错比不答更危险。

阈值设多少？ 没有通用数字，得按业务数据调：

  • 调法：拿一批「已知答案在知识库里」和「已知答案不在知识库里」的测试集跑一遍，看 Rerank 分数分布，找能把两类分开的切点
  • 经验值：一般 0.3～0.6 之间——对精度要求高（金融、医疗）偏高，对召回率宽松（闲聊型问答）偏低
  • 节奏：先从中间值开始，根据线上误判的样例往上或往下调

你可能会觉得「拒答」会让系统显得很笨。但反过来想：用户问了一个知识库覆盖不到的问题，最好的答案就是「我不知道，请联系人工」，而不是 LLM 编一个听起来合理但实际错误的回答。

防线一 + 防线二，正好各管一类幻觉：防线二负责「检索质量差时不让 LLM 胡说」，防线一负责「检索质量还行但 LLM 容易超发挥时把它框住」。 这两个是 RAG 系统上线前的基础配置，成本也最低。

四、防线三：生成后引用核查——事后审稿（最严格）

前两道防线都是「生成之前」做防控，万一还是漏了呢？防线三在生成之后做校验：

就像文章写完还要请编辑审阅一遍——防线一是事前约束作者的行为，防线三是事后审稿。

代价：多一次 LLM 调用，响应延迟增加、成本翻倍。所以一般只在对准确性要求极高的场景使用——医疗问诊、法律咨询，答错了代价很大的地方。普通的企业知识库问答，防线一 + 防线二通常已经够用。

五、防线四：结构化溯源——让每条结论都带上来源编号（格式层）

如果说防线三是在内容层面做校验，防线四就是在格式层面做约束——和防线一的「Prompt 约束」配合使用效果更好。

让 LLM 输出结构化的 JSON，每个结论都必须填写来自哪条参考资料的编号：

为什么有效？两个原因：

  1. 强制主动溯源，减少瞎编概率：LLM 在构建 JSON 时必须主动想”这条结论我从哪条资料里找到的”——就像让学生写论文必须标注参考文献，他自然就不敢随便编了
  2. 程序化验证成为可能：系统拿到 JSON 后可以自动校验，source_ids 对应的 chunk 如果和 claim 明显不相关，就自动过滤掉这条结论

用户看到答案的同时就能看到来源，可以自己去原文核实。

六、四层防线怎么组合：按场景递进

四层防线不是要全上，而是按场景从易到难递进：

场景 配置 理由
普通企业知识库 / 客服问答 防线一 + 防线二 成本极低，幻觉问题能解决大半
金融分析 / 法律文档（高可信度） + 防线四 每条答案带来源编号，用户可以自己核实
医疗问诊 / 合规审核（极低容错） 四层全上 答错代价大，用延迟和成本换最高准确性

七、灵魂总结：治幻觉，先治检索

回到开头：「检索做好了就不会幻觉」这个想法是错的——RAG 里的幻觉有两个来源，检索层没召回到内容、LLM 靠自身知识编造；以及检索到了但 LLM 超发挥、在资料基础上加了自己的推断。

最后记住最核心的一条认知——检索质量是幻觉的最大来源：

检索到了正确的内容，Prompt 再稍微约束一下，幻觉就已经少很多了；如果检索这一步就烂，再多的生成层约束也填不了这个坑。所以治幻觉，先治检索。

这和前面几篇是同一个道理：检索侧的 Query Rewrite、知识库侧的动态更新、再到生成侧的幻觉治理——RAG 的效果上限，由你解决的问题决定。
