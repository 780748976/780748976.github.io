Query Rewrite 四种策略：改写 / HyDE / Step-back / 多 Query

RAG 检索效果不好，很多人第一反应是换 Embedding 模型、调 chunk 大小——但其实很多时候问题出在最前面：用户怎么问的。用户说「这东西坏了咋整」，知识库写的是「产品故障排查与维修指南」，两句话意思明明一样，向量检索就是召不回正确文档。为什么？

因为口语表达和书面文档在向量空间里根本不是邻居。Query Rewrite 就是在检索之前，先对用户问题做加工，让它的向量坐标离正确文档更近——相当于出发前先校准导航，目的地不变，但路线更准。

一句话版本：Query Rewrite 的本质是弥合「用户提问」和「文档表述」之间的语义鸿沟，而这道鸿沟有四种形态——口语化用「直接改写」、文体差异用「HyDE」、问题太具体用「Step-back」、角度单一用「多 Query 扩展」。

一、先建立一个坐标系：为什么「意思一样」却召不回

要理解四种方法，先搞懂一个问题：为什么语义相关的两句话，向量相似度可能低到召不回来？

因为向量空间里，文本不是按”意思”分布的，而是按「表述方式」分布的。用户提问和知识库文档之间，隔着几道天然的鸿沟：

  • 口语 vs 书面：「咋整」和「维修指南」，语义相近，向量坐标相距甚远
  • 问句 vs 陈述句：问题是疑问句（「退款政策是什么」），文档是陈述句（「申请售后退款须知」），两类文体天然有坐标距离
  • 具体 vs 抽象：用户问「ef 参数设 100 合适吗」，文档讲「HNSW 参数调优原则」，粒度对不上
  • 单一 vs 多维：用户只从一个角度问，但答案涉及多个维度

Query Rewrite 的四种方法，本质上就是针对这四道鸿沟的四套加工方案——不是”改得更规范”这一件事，而是先判断鸿沟的形态，再选对应的加工方式。这是理解 Query Rewrite 的关键。

二、鸿沟①：口语化表达 → 直接改写（Query Rewriting）

最基础的一种。把口语化、模糊的问题改写成更精准、更书面化的检索表述。

改写的本质，是把口语的向量坐标拉近到文档的向量坐标——「咋退」和「申请退款的操作流程」不是同一个邻居，改写就是让前者的向量向后者靠拢。

除了口语化，它还顺手解决两类问题：

  • 补全指代：「这个功能怎么用」→ 具体功能名称，让多轮对话里的模糊引用变成检索可识别的词汇
  • 保留核心意图：去掉口头禅、寒暄，只留下检索需要的语义载荷

但直接改写只能解决口语化。还有一道鸿沟是改写搞不定的：问题和文档本来就是不同的文体——一个是疑问句，一个是陈述句。就算你把问题改写得再规范，它在向量空间里还是「问句」的坐标，文档是「陈述句」的坐标，两类文体之间天然有距离。这道鸿沟催生了 HyDE。

三、鸿沟②：文体差异 → HyDE（假设文档嵌入）

先理解一个向量空间里的经验规律：

答案到答案的距离，比问题到答案的距离近得多。

一份文档的向量坐标是「陈述句」形态。用户的问题是「疑问句」形态。哪怕语义完全相同，问句坐标和文档坐标之间也隔着一层文体距离。那怎么让检索的起点落在「陈述句」坐标上？HyDE 的思路非常巧妙：先让 LLM 生成一段假设答案，用假设答案的向量去检索文档。

很多人第一次听到会觉得多此一举：让 LLM 生成一个可能不准确的答案，再用它去检索，这不是自己骗自己吗？

关键在于：假设答案不需要准确，只需要「风格像文档」就够了。 它的作用不是回答问题，而是扮演文档的角色——充当一个向量上更好的「检索代理」。原始问题的坐标离文档远，假设答案的坐标离文档近，用后者检索命中率高得多。

HyDE 解决了文体差异，但还有一类情况它和直接改写都处理不好：用户的问题太具体了，知识库里压根没有直接对应的答案，只有相关的背景原理文档。这就要请出 Step-back。

四、鸿沟③：问题太具体 → Step-back Prompting（后退提问）

有些问题问的是具体细节，但知识库里没有直接答案，只有支撑它的背景知识。

直接拿具体问题去检索，命中不了背景文档。Step-back 的做法是：把具体问题「后退一步」，提升到更抽象的层次，先检索背景知识，再结合背景知识回答具体问题。

类比一下就很直观：就像你做一道数学题，不是一上来就硬套公式，而是先想想「这道题用的是哪种定理」，再用定理解题。知识库里没有「ef 参数设 100 是否合适」的直接答案，但一定有「HNSW 参数调优原则」这样的背景文档——把具体问题后退成背景问题，才能找到真正有用的参考资料。

前面三种方法都是在「一个问题」上做文章——要么改写它、要么给它配个假设答案、要么把它抽象化。但还有第四种情况：问题的角度本身就比较窄，一个角度去检索，覆盖面不够。这时候需要换个思路。

五、鸿沟④：角度单一 → 多 Query 扩展

前三种是「把一个问题改得更好」，多 Query 扩展是「生成多个不同角度的问题」。

用 LLM 把用户原始问题改写成 3～5 个不同角度的版本，分别去检索，再把所有结果合并去重：

核心思路：只要有一个改写版本和文档的表述对上了，就能把正确的内容召回来——就像拦截网越宽，捕到鱼的概率越高。

适用场景：用户提问风格多变、和文档表述差异大的场景，以及答案涉及多个维度的复杂问题。

代价：N 次 LLM 调用 + N 次检索——延迟和成本都随数量线性增长，需要在覆盖度和开销之间取平衡。

六、四招横向对比：各治一道鸿沟

把四种方法放在一起，选型依据一目了然：

方法 治理的鸿沟 额外开销 适合场景
直接改写 口语化、指代不清、上下文丢失 1 次 LLM 调用 多轮对话场景
HyDE 问题和文档文体风格差异大 1 次 LLM 调用 专业知识库、文体差异明显
Step-back 具体问题需要背景知识辅助 1 次 LLM 调用 技术文档、需要原理支撑的场景
多 Query 扩展 单一角度覆盖不全 N 次 LLM 调用 答案涉及多个维度的复杂问题

两个原文没细讲的决策点，值得补充：

① 四种方法不是互斥的，可以叠加。 实际系统里最常见的组合是「直接改写 + 多 Query 扩展」：先用直接改写把口语化问题规范成一个标准问句，再从这个标准问句扩展出多个角度——既解决口语化，又解决覆盖面。更极致的场景可以「改写 + HyDE + 多 Query」三件套，但每多一层就多一次 LLM 调用和检索，延迟叠加。

② 代价不是免费的。 每一种改写都是额外的 LLM 调用：

方案 每 query 新增延迟 备注
直接改写 / HyDE / Step-back +1 次 LLM 调用 几百 ms 级，通常可接受
多 Query 扩展 +N 次 LLM 调用 + N 次检索 高并发下要控制 N 和并发度

对于高 QPS 的线上 RAG 服务，这层延迟要考虑缓存策略——比如同义改写结果按 query 缓存、热点问题跳过改写直接检索。

七、灵魂总结

回到开头的问题：Query Rewrite 不是简单地把口语转成书面语就完事了。 它的核心目的是弥合「用户提问」和「文档表述」之间的语义鸿沟——而这道鸿沟有四种不同的形态，每种形态对应一种策略：

记住两条心法：

  1. 先诊断鸿沟，再选方法：不是所有问题都值得改写，先判断用户问题和文档表述之间隔的是什么——口语、文体、粒度还是角度——对症下药
  2. 改写有成本，组合要克制：每次改写都是一次 LLM 调用，多 Query 更是 N 倍放大；线上服务要考虑缓存和并发控制，不是方法用得越多越好

一句话收尾：Query Rewrite 的本质，是把「用户的问法」翻译成「知识库的写法」——四种方法对应四道鸿沟，选对方法比改得漂亮更重要。 它和上一篇的动态更新一样，都属于”检索之外的决定检索效果”的环节：上游问题不解决，下游调模型、调 chunk 都是事倍功半。
